# Настройки совместной разработки

Пользовательская инструкция: [English](../CONTRIBUTING.md) / [Русский](../CONTRIBUTING.ru.md).

Репозиторий публичный: участники делают fork и предлагают PR, владелец выбирает изменения. Доступ на запись посторонним при этом не выдаётся. Слияние PR и скачивание релизов не связаны с доступом к рабочим PLC-проектам пользователя.

## Защита main

Настройки доступны в [Settings → Rules → Rulesets](https://github.com/Svyatogor3757/vscode-step7-project-explorer/settings/rules).

Два независимых набора правил защищают `refs/heads/main`:

- **Main: owner review**: PR, одно одобрение, обязательное code-owner review, сброс одобрений после новых коммитов и закрытие обсуждений. Только владелец получает bypass в режиме `pull_request`, чтобы иметь возможность сливать собственные PR без второго аккаунта. Для остальных требуется обычное ревью владельца.
- **Main: history and CI**: запрет удаления и non-fast-forward, обязательный `windows` от GitHub Actions, актуальность относительно main. У этого набора нет bypass-исключений, поэтому проверка CI и история защищены и при PR владельца.

Созданы правила [Main: owner review, 27997788](https://github.com/Svyatogor3757/vscode-step7-project-explorer/rules/27997788) и [Main: history and CI, 27997786](https://github.com/Svyatogor3757/vscode-step7-project-explorer/rules/27997786). Исключение назначено конкретному пользователю Svyatogor3757, а не всем администраторам; это право bypass при слиянии PR, используемое для собственных PR владельца. Оно не ограничено авторством PR на стороне GitHub, поэтому владелец также должен осознанно проверять любые внешние изменения перед слиянием.

CODEOWNERS назначает `@Svyatogor3757` на все файлы. Автослияние выключено. Разрешены обычное merge, squash и rebase; владелец выбирает подходящий способ в PR. Права workflow по умолчанию – read, автоматическое одобрение PR через Actions не разрешено.

## Работа владельца и агентов

Создайте отдельную ветку, отправьте изменения и откройте PR в main. Дождитесь успешного CI. Для своего PR владелец использует предусмотренное исключение из обязательного ревью, если GitHub просит bypass; исключение применяется к этому PR, а не отключает правила репозитория.

Для внешнего PR проверьте Files changed, результаты CI и ревью. Выберите Approve, Request changes или Close; одобренный PR можно слить вручную. Новые коммиты требуют повторного одобрения. Агент не должен одобрять или сливать чужие предложения без явного поручения владельца.

Если GitHub запросит разрешение запуска CI нового внешнего участника, сначала просмотрите изменения workflow и затем разрешите запуск. Не используйте `pull_request_target` для исполнения кода чужого PR с правами записи.

## Изменение правил

При переименовании job `windows` обновите соответствующий required status check в GitHub. Проверка привязана к приложению GitHub Actions, а не к произвольному статусу с таким именем. CODEOWNERS и CI должны оставаться в base-ветке main.

Не проверяйте защиту удалением ветки или разрушительным force-push. Достаточно проверить серверные правила через API и пройти полный рабочий сценарий отдельная ветка → PR → CI → merge. Изменения этих настроек не требуют новой версии VSIX и не меняют опубликованные теги или assets.
